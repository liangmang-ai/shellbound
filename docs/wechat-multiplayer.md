# 蛋壳突围双人合作版：本地验证与微信云托管部署

本文是代码与配置的部署说明。生成代码包、通过本地测试、推送 GitHub，均不代表微信云端已经更新；云端部署和小游戏上传是后续单独操作。

## 现有环境

| 项目 | 值 |
| --- | --- |
| 小游戏 AppID | `wx1a1efb651d164fae` |
| 微信云托管环境 | `prod-d8gczi3gb667c244b` |
| 服务名称 | `express-9qmf` |
| 云端健康检查 | `GET /healthz` |
| 游戏实时连接 | `/ws` |

复用当前 Express 示例服务即可，不需要另建数据库。双人版房间、玩家和战斗状态放在单个服务实例内存中，不读取 MySQL。模板已经创建的 MySQL 不会被程序删除或更改；如果日后不再使用，可由账号所有者另行确认其保留与费用安排。数据库密码、微信密钥及账号凭证不应写进源码、部署包或截图。

## 部署模型与限制

- 两台手机通过房间码进入同一房间，由服务端计算移动、怪物、伤害、掉落和波次，客户端发送操作并显示同步结果。
- 这版只支持单实例。最大实例数必须设为 `1`，同时只能有一个版本接收游戏流量。不同实例或不同灰度版本的内存房间彼此不可见，会导致同一个房间码找不到房间。WebSocket 的单连接保持不等于两名玩家会进入同一实例。
- 建议测试期间最小实例数也设为 `1`，避免冷启动。常驻实例会持续消耗计算和内存额度；免费期、剩余额度及超额计费以当前控制台为准。若手动改为最小 `0`，需接受无请求缩容后的冷启动，不能依靠内存保留房间。
- 重启、发布、缩容或实例故障会结束该实例内的房间，本版不提供跨进程战局恢复。发布前应让正在游戏的玩家退出，新版本切到 `100%` 流量后再重新开房；旧连接不会因为发布自动迁移到新战局。
- 本版没有跨实例匹配、在线排行榜或全球低延迟调度。头像昵称授权与好友榜已暂时撤下，房间使用默认蛋形头像和玩家编号。房间数量上限是保护阈值，实际承载能力需真机及负载测试确认。

## 准备本地代码包

联机服务需要 Node.js 22 或更新版本，以及系统 `zip` 命令。容器镜像使用 Node.js 22。

```sh
npm install
npm --prefix server ci
npm test
npm run build
npm run test:coop
node scripts/package-server.mjs
```

构建游戏时会保留 `dist/wechat` 内用户已有的 Git 仓库与工程设置。

最后一条命令只白名单打包服务端运行文件及共用的战斗规则，输出：

```text
artifacts/shellbound-coop-server.zip
artifacts/shellbound-coop-server/
```

包根包含 `Dockerfile`，构建上下文为包根。包内没有 `.git`、`dist`、浏览器素材、`node_modules` 或数据库配置。使用本地代码包可以避免给云托管额外授权个人 GitHub 私有仓库。

在完整仓库中自行构建镜像时，命令为：

```sh
docker build -t shellbound-coop .
```

## 绑定个人 GitHub，之后直接执行流水线

首次 ZIP 部署成功后，可以把后续发布来源改成 GitHub。使用个人账号 `xykyankun` 授权访问私有仓库 `xykyankun/shellbound`；GitHub 授权页确认账号和仓库范围，不要选择公司仓库。

在服务 `express-9qmf` 的「服务设置 → 流水线」中配置：

| 字段 | 值 |
| --- | --- |
| 代码源 | GitHub |
| 代码仓库 | `xykyankun/shellbound` |
| 分支 | `codex/shellbound-mvp` |
| 目标目录 | 留空，使用仓库根目录 |
| 端口 | `8080` |
| Dockerfile 文件 | 有 |
| Dockerfile 名称 | `Dockerfile` |
| 推送触发 | 初次配置先不勾选，保留手动发布 |

`Dockerfile` 位于仓库根目录；构建上下文也必须是仓库根目录，容器构建需要同时读取 `server/` 与 `src/` 中的文件。不要将目标目录选成 `server/`。

后续流程是：代码修改完成并通过验证、连续三轮审查后，提交并推送个人仓库；然后在「部署发布 → 发布」里选择「执行流水线」，由云托管拉取配置分支中的代码、构建镜像并发布。无需重新打包或上传 ZIP。发布时确认选择的是本次要上线的提交，保留单实例、唯一版本接收流量及原有生产环境变量的配置。

保存流水线配置和向 GitHub 推送代码，都不等于云端已经发布。这份配置只准备手动触发的流水线，不设置 push 自动部署。发布会结束现有实例中的战局，建议在没有玩家进行游戏时更新。

如以后明确需要推送即上线，可在控制台勾选「推送触发」。官方说明此开关会在对应分支 push 或 merge 后自动构建、部署并全量发布，并非只构建待确认的版本；启用后要将每次推送都视为一次线上发布，不要删除云托管创建的 GitHub webhook。

该方式只更新联机后端；小游戏客户端界面或玩法修改后，仍需在微信开发者工具编译、上传体验版，并按需要完成审核发布。官方流程见[服务设置：流水线](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/service/pipeline.html)和[部署发布](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/service/online.html)。

## 云托管配置

进入现有服务 `express-9qmf`。不要删除当前环境，也不要选择再次初始化模板。

1. 在「服务设置」关闭「公网访问」。生产连接只通过小游戏内的 `wx.cloud.connectContainer` 进入微信网关。
2. 将最大实例数设为 `1`，建议测试期最小也设为 `1`；关闭可能增加副本数的定时扩容规则。先以小规格测试，再根据监控调整单个实例规格。
3. 配置下文的生产环境变量，端口设为 `8080`，健康检查使用 HTTP `GET /healthz`。
4. 选择「部署发布」→「手动上传代码包」，上传 `artifacts/shellbound-coop-server.zip`。目标目录为根目录，Dockerfile 为根目录的 `Dockerfile`。
5. 确认新版本启动日志与健康检查通过，将该版本切为唯一接收流量的版本。此后再用小游戏真机测试开房和加入；该内存房间版本不采用同时分流给两个版本的灰度方式。

官方说明：本地上传支持文件夹和 ZIP，代码包限制为 2 MiB；服务端口必须与容器监听端口相同。参见[部署发布](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/service/online.html)与[服务设置](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/service/pipeline.html)。

服务环境变量：

| 名称 | 生产值 | 说明 |
| --- | --- | --- |
| `NODE_ENV` | `production` | Dockerfile 已设置 |
| `PORT` | `8080` | Dockerfile 已设置；控制台端口与此保持一致 |
| `TRUST_WECHAT_HEADERS` | `1` | 显式启用微信网关身份校验，必须配合关闭公网访问 |
| `WECHAT_APP_ID` | `wx1a1efb651d164fae` | 只接受当前小游戏的微信身份 |
| `ROOMS_MAX` | `5` | 建议初测先用 5，代码默认 20；保护阈值不是承载量保证 |
| `DEV_MODE` | 不设置 | 生产环境不得设为 `1` |

不需要配置数据库账号、数据库密码或客户端密钥。没有显式启用生产鉴权时，服务会启动失败，避免误开放匿名联机。等待队友超过 5 分钟或单次暂停超过 10 分钟后，房间会结束；任一方离开或断线会结束本局，每名玩家分别保留 3 次免费复活。两人可以分别发起暂停，各自解除自己的暂停请求，全部确认继续后才恢复战斗。

## 本地双浏览器联调

在两个终端分别运行：

```sh
npm run server
```

```sh
npm run dev
```

然后打开两个 `http://127.0.0.1:5173/` 页面。两边均点击「双人合作」，一边「创建房间」，另一边输入 6 位房间码加入，两人到齐后由房主开始。

本地联机地址固定为 `ws://127.0.0.1:8787/ws`。本地服务只监听回环地址，并拒绝非本机来源；无法用手机访问电脑局域网 IP 联调。生产浏览器页面也不提供云端联机入口，微信真机通过原生 `wx.cloud.connectContainer` 调用环境 `prod-d8gczi3gb667c244b` 中的 `express-9qmf` 服务。

### 微信身份与公网开关

服务端生产模式要求显式开启微信网关身份校验，并检查微信用户 OpenID、小游戏 AppID 和调用来源。`X-WX-*` 身份头仅在已关闭公网、经微信网关转发的部署下信任；仅检查普通 HTTP 头不能作为任意公网来源的身份认证。

官方文档列出 `X-WX-OPENID`、`X-WX-APPID`、`X-WX-SOURCE` 等[容器内微信信息](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/development/weixin/)，并建议仅微信调用的服务[关闭公网访问](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/development/call/mini.html)。客户端不能填写一个自选 OpenID 来代替微信身份。

特别注意：官方[WebSocket 接入说明](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/development/websocket/miniprogram.html)注明，iOS「高性能+」模式的 `connectContainer` 暂时无法携带微信身份。这版遇到身份缺失时会拒绝联机，不会退回匿名连接；iOS 真机必须验证当前运行模式及身份传递。

关闭公网后，浏览器直接打开服务公网域名可能失败，这不等于小游戏的云连接失败。需要通过真实小游戏的云连接验证。`/healthz` 不要求玩家身份，但仍受云托管公网访问开关限制。

### 创建或加入房间失败

同一个微信账号同时只能保持一个联机连接。手机已创建房间时，使用同一微信账号登录的开发者工具无法作为第二名玩家加入；服务端会在 WebSocket 握手时返回 `409`。双人测试须使用不同微信账号，或先退出原连接再在另一端进入。客户端会从结构化状态或明确的握手状态文本中提取 `HTTP_409` 并提示账号冲突，不会自动重试或踢掉原连接。

客户端把云初始化、云连接、WebSocket 握手与房间响应分开计时，后面三个阶段各等待最多 15 秒。连接失败提示保留阶段与安全错误码，不显示可能包含身份或签名地址的原始 SDK 信息。连接关闭会保留 WebSocket 状态码。错误码为 `UNKNOWN` 时，现有信息不足以判断是网络、部署还是身份问题；不会统一归因为 iOS 高性能模式。

根据官方[调用服务常见问题](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/development/call/faq.html)，`102002` 表示请求超时，`SERVICE_NOT_READY` 可能发生在服务冷启动时。客户端仅在尚未发送创建/加入请求时，对这两类暂态错误或本地连接超时自动重试一次。已经发出房间请求后，不会盲目重试，避免重复建房；权限或环境配置错误也不会自动重试。取消连接会撤销待执行重试，迟到的旧连接会被关闭。

官方 `connectContainer` 示例仍要求在返回的 `socketTask` 上等待 `onOpen` 再发送数据。这版继续遵循该流程，先注册消息、错误和关闭监听；不会根据 Promise 已返回就假设 WebSocket 已打开，也不会改走匿名公网连接。上述处理只增强暂态容错与诊断，仍需用新版客户端在手机上复测实际错误码，才能确认线上失败原因。

## 联机画面与性能排查

服务端每秒模拟 30 次、广播 20 次状态。客户端通过约 75 毫秒的显示缓冲，把收到的位置平滑到设备的画面刷新频率；伤害、弹药、复活与碰撞仍以服务端状态为准。暂停、死亡、复活、传送和穿越障碍的轨迹会直接对齐，避免把旧位置拖到新战场。当前没有本地移动预测，显示平滑不能消除网络本身的操作延迟。

新版客户端会协商精简快照：地图和难度在首帧发送后复用，玩家和环境状态也不重复编码。旧客户端继续收到完整格式，新客户端连接旧服务端也可以运行。因此客户端和后端可分别更新；要获得两项优化，需要执行后端流水线，并在开发者工具重新上传新版客户端。

浏览器调试控制台可读取 `globalThis.__shellbound.getSnapshot().performance`。`fps` 与 `frameMs` 反映画面回调频率，`network.snapshotIntervalMs` 为最近两帧有效状态的到达间隔，正常广播约为 50 毫秒；`snapshotBytes` 是最新同步帧大小，`rttMs` 为心跳往返时间，首次测量需等待约 15 秒。读数不会显示在正式游戏界面，断线后网络指标会清空。微信真机绘制帧率需结合开发者工具的性能面板观察。

CPU、内存平均使用率较低，仍可能有网络抖动或手机绘制掉帧。应结合帧率、到包间隔和往返时间判断，不用单个平均利用率决定升配。单实例最大房间数是保护阈值，0.5 核、1 GiB 的实际容量仍需在该规格下压测确认。

## 上线前真机检查

- 在两台不同微信账号的手机上打开同一体验版。由一人创建房间，另一人输入房间码；错误房间码与满员提示均应可理解。
- 两人进入同一地图与难度，确认彼此移动、射击、手雷、爆发、怪物伤害、掉落和波次一致，单人模式仍可正常开始。
- 检查死亡、复活、退出房间、切后台和网络断开后的提示，不把断线画面误认为仍在进行的有效战局。
- 重启服务后重新开房，确认旧房间无法继续；检查新旧版本流量仅剩一个版本。
- 查看云托管 CPU、内存、连接数、流量与额度消耗。通过这一步才能判断免费额度是否覆盖实际使用，不能用本地测试结果推断线上零费用。

云端部署、微信开发者工具上传体验版、两台手机联调、提交审核和正式发布是不同阶段。完成前一阶段不表示后一阶段已完成。
