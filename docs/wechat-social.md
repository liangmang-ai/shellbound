# 微信头像昵称与好友榜

## 本版行为

- 合作页面和好友榜提供「授权微信头像昵称」。玩家主动点击后由微信处理隐私同意和资料授权，拒绝仍可用游客身份游玩。首次同意隐私后，如按钮仍显示授权，再点击一次微信原生按钮完成资料授权。
- 合作房间显示双方昵称与头像，战斗人物上方显示昵称。未授权或头像加载失败时使用游客名和蛋形头像。
- 好友榜分为单人、双人 × 休闲、标准、挑战，共六榜。分数高者优先，同分比较最高波次。双人使用队伍总分，显示双方；两位好友保存的同局成绩会合并成一条队伍成绩。
- 单人阵亡、双人全队阵亡时尝试同步成绩。复活后获得更高成绩会更新，同一成绩不会反复提交。每人每个榜只保存一条最佳成绩；双人榜不是所有历史队伍的战绩列表。
- 尚未同意微信隐私说明时，六榜各自的最高待同步成绩暂存当前会话内存，不弹窗打断游玩。之后主动授权或打开好友榜并同意隐私，才补交；退出前未授权的待同步成绩会丢失。单人原有本机最高纪录继续保留。
- 榜单可翻页，包含使用本游戏并留有相应成绩的微信好友。浏览器只展示进入微信查看的提示。

## 发布前由管理员完成

1. 在小游戏后台更新「用户隐私保护指引」，声明「昵称、头像」和「微信朋友关系」：头像昵称用于合作房间、人物标签及好友榜；微信朋友关系用于获取和展示同玩好友成绩。并在「基本设置 → 隐私授权弹窗」开启平台统一弹窗，本版没有自定义隐私弹窗。资料为可选项，不收集手机号、通讯录或定位。`getPrivacySetting` 返回 `needAuthorization:false` 也可能是后台未填写隐私项目，不能作为已完成配置的证明。
2. 用当前个人 GitHub 分支执行云托管部署流水线，使房间服务支持双方公开资料与同局编号。无需新增 MySQL 表或修改云服务规格。
3. 执行 `npm run build`，在开发者工具中编译 `dist/wechat` 并上传新客户端。构建包含 `open-data/index.js`，`game.json` 已配置 `openDataContext`，无需另外创建开放数据域工程。
4. 用两个微信好友账号测试：拒绝授权仍能开房；分别授权后在房间中看到对方；完成一局后打开对应模式/难度好友榜；确认分数、波次与两位队友；检查其他模式/难度互不混排、翻页正常、较低成绩不覆盖原纪录。
5. 测试断网时结算、复活与返回战区仍可用，恢复网络后重新打开好友榜重试同步。真实微信授权、朋友数据和云存储写入必须在平台上验证，本地模拟接口测试不能替代这些检查。

## 数据边界

房间鉴权继续使用原有云托管身份机制。昵称与头像只是显示资料，不用于验证玩家身份；服务端仅保留经过长度和地址限制的两项公开资料，头像只接受 HTTPS 微信头像域名，服务端不下载头像。房间消息不包含 OpenID、登录凭据或会话密钥。

原始朋友关系、朋友 OpenID 和平台朋友资料仅在微信开放数据域内处理，不回传主游戏或房间服务器。主游戏只传入当前成绩和玩家已同意展示的资料；好友榜绘制结果通过共享画布展示。成绩采用六个 `shellbound.v1.*` 云存储键，每条键和值合计不超过 1024 UTF-8 字节，开放数据域先读取旧最好成绩，再决定是否写入；读取失败时保留云端旧纪录并重试。

此榜接受客户端上报，不能防作弊，也不能保证同一账号在多台设备同时写入时的原子性。它不包含公开全服排行，不引入排行榜数据库或额外房间实例；云存储和关系 API 的实际额度、权限与计费以微信后台为准。
